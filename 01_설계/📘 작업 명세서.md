# 사람이 승인하는 일정 등록 에이전트 작업 명세서

> 작성일: 2026-11-09 (Asia/Seoul)
> 상태: 초기 요구사항 기록. 구현·설치·계정 인증·실제 일정 등록은 아직 하지 않았습니다.
> 관련 문서: [진행 현황](<📋 진행 현황.md>)

## 1. 목표

공지문을 입력하면 AI가 일정 정보를 추출하고, 계산 가능한 위험 기준에 해당하는 건만 사람에게 확인받은 뒤 Google Calendar에 등록하는 과제입니다.

새 캘린더 앱을 만드는 것이 아닙니다. 과제의 웹 화면은 공지 입력·검토·처리 기록을 담당하며, 최종 일정의 저장 대상은 실제 Google Calendar입니다. 로컬 DB 등록이나 가짜 성공 화면을 Google Calendar 연동 성공으로 대신하지 않습니다.

분류: 노드 과제·실습. 기준 노드: `에이전트 팀 꾸리기_Agt2 / 9.사람이 승인하는 에이전트 만들기 [프로젝트]`.

## 2. 사용자 확정 사항과 이번 승인 범위

| 항목 | 확정한 내용 |
|---|---|
| 업무 | 공지문에서 일정·마감을 추출하고, 필요한 건을 사람에게 확인받아 기존 캘린더에 등록 |
| 제공자 | Google Calendar |
| 작업 위치 | `02_노드실습/261109_일정등록_에이전트/`의 새 과제 폴더 |
| 문서 | `01_설계/📘 작업 명세서.md`, `01_설계/📋 진행 현황.md` 생성 |
| 도구 연결 | 앱 내부 함수/API 방식. 별도 MCP 서버는 만들지 않음 |
| Git | 이 과제 폴더의 새 단독 저장소, `.gitignore`와 `CHANGELOG.md`, 검증 단위별 로컬 커밋 |
| 공개 범위 | 원격 저장소 생성·push·태그·배포는 승인하지 않음 |

이번에 구체적으로 승인받은 변경은 폴더·문서·Git 준비입니다. 패키지 설치, 앱 구현·기동, 모델 호출, Google Cloud 설정 변경, 계정 권한 부여, 캘린더 조회·일정 생성은 다음 승인 게이트입니다. 일반적인 진행 동의를 외부 데이터 변경 승인으로 확대하지 않습니다.

## 3. 사용자 흐름

1. 사용자가 공지 원문과 날짜 해석의 기준 정보를 입력합니다.
2. AI가 일정 후보와 원문 근거를 추출합니다. AI는 날짜나 필수 정보를 임의로 확정하지 않습니다.
3. 코드가 필수 정보·날짜의 유효성·승인 기준을 검사합니다.
4. 기준에 해당하지 않는 유효한 건은 지정된 Google Calendar에 자동 등록합니다.
5. 기준에 해당하는 건은 등록 전에 멈추고 대기 상태를 저장합니다.
6. 사람이 원문·일정 후보·근거·멈춘 이유·등록 시 결과를 보고 결정합니다.
7. 승인 또는 수정 후 승인된 건만 해당 내용으로 등록하고, 반려된 건은 등록하지 않습니다.
8. 실제 생성된 일정의 ID로 재조회하고, 승인 내용과 저장된 제목·날짜·시간 등이 일치하는지 확인합니다.

자동 처리 경로는 제품의 요구사항입니다. 개발 중 첫 실등록 시험의 별도 승인은 제품에서 모든 일정을 사람이 승인하도록 바꾸는 근거가 아닙니다.

## 4. 과제 필수 요구사항

| ID | 요구사항 | 최종 증거 |
|---|---|---|
| R1 | 실제 외부 반영 직전의 멈춤·재개 | 승인 전 Google 일정 미생성, 응답 후 해당 요청의 실행 재개 |
| R2 | 승인 기준에 걸리지 않은 건의 자동 처리 | 웹 입력부터 실제 Google 일정 생성·재조회까지 사람 확인 없이 통과한 사례 |
| R3 | 계산 가능한 승인 기준 두 가지 이상과 위험 설명 | 기준 정의, 각 기준이 막는 위험, 자동 통과가 타당한 사례 |
| R4 | 대기 상태 보존 | 요청별 실행 식별자, 영속 체크포인트, 앱 재시작 후 대기 건 복원·처리 |
| R5 | 로컬에서 사용할 수 있는 웹 데모 | 대기 목록, 건별 검토, 승인·반려 및 결과 확인을 실제 브라우저에서 실행 |
| R6 | 승인 화면의 판단 재료 | 요청 원문, 핵심 일정 정보, AI 해석과 근거, 멈춘 이유, 승인 시 실제 반영 내용 |
| R7 | 기준 검증과 실행 결과 기록 | 같은 평가 사례에 기준 후보를 적용한 개입률·놓침·헛멈춤 비교 및 실제 실행 기록 |
| R8 | 제출물 | 실행 코드, 실행 방법의 `README.md`, 원문이 요구하는 항목을 갖춘 `REPORT.md`, 최종 GitHub URL |

공개 앱 배포는 수업의 필수가 아닙니다. 실행 코드의 GitHub 제출과 웹앱의 인터넷 배포는 다른 단계입니다.

## 5. 승인 기준 초안 — 아직 사용자 확정 전

| 후보 | 계산 가능한 형태로 구체화할 방향 | 막으려는 위험 |
|---|---|---|
| A. 일시 정보 부족·모호함 | 원문 근거 없는 날짜·시각, 필수 정보 누락 등 명시적 검증 결과가 존재하면 검토 요청 | AI가 추측한 일시에 등록 |
| B. 기존 일정과 시간 충돌 | 승인된 조회 범위의 기존 일정과 후보의 시간 구간이 겹치면 검토 요청 | 이미 예정된 일과 중복 예약 |

위 두 기준은 현재 제안이며, 확정된 알고리즘이나 검증 완료 결과가 아닙니다. 종일 일정, 마감 시각만 있는 공지, 상대 날짜, 일시 변경 공지는 실제 입력 사례를 확인한 뒤 다룰 범위를 정합니다.

검증에서 사용할 사람 검토 필요 정답은 모델 자신의 확신도와 별도로 정합니다. 같은 자료로 기준을 조정하고 평가했다면 그 한계를 보고서에 적습니다. 사례 수·정답 작성 방식·호출 상한은 아직 정하지 않았습니다.

- 개입률: 전체 중 사람 검토 대상으로 보낸 비율.
- 놓침: 사람이 봐야 하는데 자동 처리한 건수.
- 헛멈춤: 자동 처리해도 되는 건을 검토 대상으로 보낸 건수.

유효하지 않은 일정은 단순 승인만으로 등록하지 않으며, 필요한 정보 수정 후 다시 유효성을 확인합니다.

## 6. 승인 응답과 상태 보존

강의 4강은 승인·수정 후 승인·반려·다시 판정의 네 응답과 후속 처리를 설명합니다. 프로젝트 필수 구현 문구는 승인이나 반려 같은 답을 받을 수 있어야 한다고 표현합니다. 네 응답 전체의 적용 범위와 재판정 횟수 제한은 기술 설계 전 확정할 항목이며, 최소 문구와 강의 권장 설계를 혼동하지 않습니다.

대기 상태는 메모리만이 아니라 파일 또는 DB에 남겨 재시작 후 복원할 수 있도록 설계합니다. 대기 시간 초과 시 자동 승인할지 등 운영 정책은 아직 미정입니다.

LangGraph의 재개 시 중단된 노드가 처음부터 다시 실행될 수 있습니다. 일정 생성 같은 외부 변경을 승인 노드의 `interrupt()` 앞에 두지 않고 별도 실행 단계로 분리합니다. 중복 클릭·응답 유실·재시도에 따른 중복 등록도 설계·검증 대상입니다.

## 7. 첫 버전의 경계

- 별도 캘린더 앱, MCP 서버, 공개 호스팅은 이번 제안 범위에서 제외합니다.
- 공지 입력은 직접 붙여넣기를 시작점으로 제안합니다. 메일·메신저 자동 수집은 현재 합의 범위가 아닙니다.
- 기존 Google 일정의 임의 수정·삭제, 참석자 초대·외부 알림 발송은 현재 승인 범위가 아닙니다.
- 실제 등록 대상 캘린더, 충돌 확인을 위한 조회 범위, 첫 시험 일정의 내용·개수·정리 방법은 실연동 전 별도 승인받습니다.
- 모델 제공자·모델·인증·비용·원문/일정 정보의 전송 범위는 미정입니다. 로컬 웹앱이라고 로컬 LLM을 쓰는 것은 아닙니다.
- 인증값은 코드·문서·로그·Git에 넣지 않습니다. 공급자 인증 JSON이 필요한 경우 보관 방식과 Git 제외를 먼저 확인받습니다.

## 8. 루브릭과 보고서

| 평가 기준 | 연결 요구사항 | 확인할 증거 |
|---|---|---|
| 웹 데모와 제출물의 완결성 | R5, R6, R8 | 실제 승인 화면 사용, 구조도·기준·실행 결과가 있는 보고서 |
| 승인 기준 설계의 타당성 | R3, R7 | 기준 두 가지 이상, 각 위험 설명, 기준 후보 비교 |
| HITL 파이프라인 구현의 정확성 | R1, R2, R4 | 외부 반영 전 멈춤·재개, 자동 처리 경로, 대기 보존 |

`REPORT.md`의 원문 요구 항목은 주제와 이유, 파이프라인 구조도, 승인 기준과 이유, 실행 결과, 데모 화면 설계와 캡처, 프로젝트 회고입니다. 구조도는 Mermaid 또는 이미지로 작성할 수 있습니다. 회고·기준 선택 이유 등 사용자 판단은 사용자 작성과 에이전트 사실 기록을 구분하며 임의로 사용자 의견을 만들어 넣지 않습니다.

LMS 프로젝트 안내는 GitHub 저장소 주소 제출을 요구합니다. 별도 제출 화면에는 파일 또는 URL 한 가지 방식만 가능하며 제출 후 수정할 수 없다는 안내가 있습니다. 제출 버튼은 사용자가 최종 확인합니다.

## 9. 다음 승인 게이트와 실행 순서

1. 실제 입력 예시를 확인하고 승인 기준·응답 범위·기준 날짜 해석을 확정합니다.
2. Google 계정 연결 방식·대상 캘린더·조회 권한 범위, 모델·호출 상한을 정합니다.
3. 실제 연결 경계를 조사한 뒤 별도 기술 명세서 작성과 앱 구현 범위를 승인받습니다.
4. 격리 환경과 최소 패키지의 설치 범위를 승인받습니다.
5. 승인된 소량의 실연동 시험으로 실제 Google 일정 생성·재조회부터 확인합니다.
6. HITL·웹 화면·상태 보존과 기준 비교를 구현·검증합니다.
7. README·REPORT·실행 증거를 정리하고, 공개 파일 목록을 확인받은 뒤 GitHub 제출을 준비합니다.

초기 안내한 전체 예상은 1~3시간이며 계정 설정 대기는 별도입니다. 아직 실제 소요시간을 측정한 값이 아니며, 인증·연동 제약이 확인되면 다시 추정합니다.
