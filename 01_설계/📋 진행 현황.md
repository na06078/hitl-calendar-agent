실제 공개 메서드·DTO·설정 로더와 화면을 대조해 `.env`·예시를 준비했고, 실제 서비스·SQLite·LangGraph와 외부 대역을 붙인 소비자 통합을 검사했습니다. 추가 4개 중 정상 경로와 가드 음성 대조 2개는 검증 사례, 공개 오류 DTO 표시·잘못된 시간대 정규화 2개는 실제 행동 RED→GREEN을 관찰했습니다.

초기 전체 기록은 `.local/메인_전체검증.json`, 보완 이력은 `.local/메인_수정후검증.json`과 `.local/검토_조치.json`입니다. 최신 전달 실행기는 `02_구현/테스트실행.py`, 전체 결과는 `.local/최근_테스트.json`입니다. 현재 기대/실행 64개·고유 식별자·소스 해시·시험 중 소스 불변을 확인했습니다. 상속 PYTHONPATH가 Hermes 패키지를 혼입한 첫 진단 실패는 앱 실패가 아니며, 프로젝트 Python의 `-I` 격리 실행으로 바로잡았습니다. 패키지 재설치·전역 환경 변경은 없습니다.

초기 실제 브라우저 기록은 `.local/브라우저검사/검사결과.json`과 `채택결과.json`, 실행기는 `.local/브라우저_검사.py`입니다. 새 공지·대기/기록 빈 상태·미제출 입력 보존·준비 표시·실제 서비스 close/cache clear/재생성·390px 가로 표시·하단 버튼 스크롤을 확인했습니다. 분석·Google 연결·일정 반영 버튼은 누르지 않았으며 장부 전후 0을 확인했습니다. 스크롤 검사의 초기 DOM 판정은 캡처와 맞지 않아 채택하지 않고 이력에 보존했습니다. 양수 크기 버튼·즉시 스크롤과 날짜 위젯/글꼴 준비를 검사기에 추가한 뒤 실제 캡처를 다시 읽었습니다. 최초 스크롤 불일치의 원인을 숨은 노드나 지연 동작 중 하나로 단정하지 않습니다.

사용자 접속 주소는 `http://127.0.0.1:8501/`입니다. 기존 실행 작업이 현재 도구에서 not_found이고 포트 수신이 없어 종료 원인을 확정하지 않고 앱을 재기동했습니다. 새 작업은 `proc_9c5386616669`, 격리 Python `-I`와 같은 loopback·통계 끔 설정입니다. 보안값 교체·반복 로그인은 하지 않습니다. 승인된 첫 시험의 원문·상한·기존 장부 0 기준·소유 ID·정리 목록은 `.local/실연동검증/범위.json`에 기록합니다. 분석 제출 한 번만 허용하고 5개 후보 상한을 지키며, 재판정까지 누적 모델 3회 범위입니다.

관찰된 RED→GREEN을 기록하고 import 오류를 행동 테스트의 RED로 세지 않습니다. 자녀 결과를 기다리려고 로그·산출물을 반복 조회하지 않으며, 메인은 독립 화면 작업을 진행한 뒤 정상 결과 전달을 받습니다.

설치와 외부 호출은 별도입니다. 설치 승인만으로 서버·브라우저·Google 로그인·모델·캘린더 요청을 시작하지 않습니다. 모델·Google 연결부는 테스트에서 명시적 대역을 쓰고 실제 전송을 막습니다.

Cloud 준비 기록은 `.local/구글_클라이언트_준비.json`입니다. 과제용 Desktop app의 이름은 `일정 등록 에이전트`입니다. 생성 화면의 AI 옵션 도움말은 Google MCP 사용 시 선택하라고 안내하므로, 직접 Calendar API를 쓰는 이번 앱에서는 선택하지 않았습니다. 기본 저장 도구의 요소 인자 변환 오류는 수정하지 않았고, 정확한 저장 대화상자의 Windows 기본 API로 경로를 읽어 확인한 뒤 영구 파일을 저장했습니다. 생성·파일 저장·앱 인증·Calendar 실호출은 각각 구분합니다.

모델은 `gpt-5.6-luna`로 사용자 확정됐으므로 선택 질문을 반복하지 않습니다. 이전 `gpt-6-luna` 추천은 과거 비교 기록으로만 남깁니다. 공식 표준 요금과 예시 계산은 작업 명세서 9절에 있으며 실제 추론·혜택 적용 증거가 아닙니다.

등록 대상은 사용자 선택대로 `primary`입니다. 새로운 캘린더나 기존 앱을 별도로 만들지 않았습니다. 개인 일정 내용은 모델에 보내지 않고 코드가 가용 시간만 조회합니다.

그다음 실제 입력 예시, 승인 기준 두 가지, 사용자 담당 판단, 기술 명세서와 구현 범위를 확정합니다. 모델·계정 준비가 안 됐다는 이유로 이미 합의한 요구사항을 처음부터 다시 인터뷰하지 않습니다.

## 7. 주요 결정 이유·한계·보류

- 기존 프로젝트에 억지로 붙이지 않고 독립 과제로 분리: 기존 기능의 범위와 회귀 부담을 늘리지 않기 위함.
- Google Calendar 실연동 유지: 실제로 쓸 수 있는 보조 에이전트를 만들려는 사용자 목표.
- 앱 내부 함수/API: 이번 과제에 별도 MCP 서버 운영을 추가하지 않음.
- 사람 검토 기준은 일시 정보 모호함과 일정 충돌을 첫 버전 기본값으로 구현·오프라인 검증함. 실제 업무 자료·사용자 정답에 대한 타당성 평가는 아직 전.
- 원문 근거·코드 검증·사람 결정·외부 반영 기록을 구분. LLM의 확신도만으로 안전을 보장하지 않음.
- 기존 일정 수정·삭제, 참석자 초대, 메일·단체방 자동 수집, 공개 호스팅은 현재 범위 밖.
- 사용자 선택 이유·평가 정답·회고를 에이전트가 사용자 의견으로 임의 작성하지 않음.
- 기술 명세서 작성과 코드 범위는 승인됐으며 초안을 작성함. 후속 구현은 이 연결 계약을 읽고 실제 의존성 API와 재대조.
- 초기 전체 예상 1~3시간은 추정이며, 인증 설정 대기는 별도. 구현 소요시간 실측은 아직 없음.
- UI는 PC용 Streamlit 표준 컴포넌트로 단순화. 390px에서 큰 제목 마지막 글자의 다음 줄 배치는 미세 조판 보류 항목이며, 기능 가림은 확인되지 않음. 실제 대기 건의 긴 근거·오류·수정 폼은 실연동 뒤 별도 검사.
- 생성 후 본문 읽기 사고는 보존하며 도구의 open 성공만으로 실제 읽기 대상 전환을 가정하지 않습니다. 사용자가 현재 값을 유지하기로 결정했으므로 교체 대기는 해제했습니다. 원시 값은 문서·Git·별도 기록에 복사하지 않습니다.

## 8. 재개 방법

프로젝트 루트에서 작업 명세서·기술 명세서·이 현황·CHANGELOG와 실제 파일을 함께 확인합니다. Git은 승인된 로컬 방식대로 사용하되 기존 변경을 먼저 구분합니다. 코드·오프라인 시험·초기 실제 화면·실계정 성공을 구분하고, 서버의 현재 생존은 포트/HTTP로 다시 확인합니다. 문서의 시험 계획을 실행 증거로 취급하지 않습니다.
