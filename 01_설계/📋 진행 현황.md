## 6. 다음 구체적 단계

설치 작업 `proc_cb315e69376e`는 종료 코드 0이고, 과제 Python에서 패키지 86개·직접 버전 8개 일치·호환성 검사 PASS를 확인했습니다. 공개 OpenAI Responses 인자와 Google 로컬 OAuth timeout 인자도 해당 환경에서 확인했습니다. 기초 결과는 `.local/환경확인.json`, 버전 잠금은 `02_구현/의존성_잠금.txt`입니다.

배정 `deleg_f9531f9f`의 서브에이전트 `sa-0-86eab123` 결과를 받았습니다. 인계 `.local/백엔드_인계.json`의 13개 파일 해시가 일치했고, 기존 40개를 메인에서 같은 식별자로 재실행해 통과했습니다. 원래 자녀 기록을 덮어쓰지 않고 `.local/메인_백엔드검증.json`에 재실행 결과를 보존했습니다. 자녀가 기록한 RED→GREEN 20개는 자녀의 역사적 기록이며 메인이 그 모든 RED를 직접 재실행했다고 주장하지 않습니다.

독립 검토 `deleg_c64aa0bc`의 원 결과는 `.local/독립검토.json`입니다. Standards passed / Spec changes_needed 2건을 받았고 원 판정·파일을 바꾸지 않았습니다. CAL-01의 매일 반복 입력이 실제 대역 Google 쓰기로 이어짐을 재현한 뒤 검토 중단으로 바꿨습니다. 알려진 반복 표현과 반복 단어 없는 교차일 시간 후보도 검사하며, 단일 시간·다일 종일 양성 경로를 유지했습니다. CAL-02는 부모가 먼저 재현한 시간대 예외와 일치했고 APP_TIMEZONE 수정 안내를 포함하는 공개 오류로 정리했습니다. 원 검토와 부모 재검증은 별개입니다.

실제 공개 메서드·DTO·설정 로더와 화면을 대조해 `.env`·예시를 준비했고, 실제 서비스·SQLite·LangGraph와 외부 대역을 붙인 소비자 통합을 검사했습니다. 추가 4개 중 정상 경로와 가드 음성 대조 2개는 검증 사례, 공개 오류 DTO 표시·잘못된 시간대 정규화 2개는 실제 행동 RED→GREEN을 관찰했습니다.

초기 전체 기록은 `.local/메인_전체검증.json`, 보완 이력은 `.local/메인_수정후검증.json`과 `.local/검토_조치.json`에 보존합니다. 최종 전달 실행기는 `02_구현/테스트실행.py`, 최신 전체 결과는 `.local/최근_테스트.json`입니다. 기대/실행 62개·고유 식별자·소스 해시·시험 중 소스 불변을 확인했습니다. Windows asyncio의 stdlib socketpair까지 무차별 차단했던 초기 실패는 scaffold 문제이며 앱 RED로 세지 않았습니다. 자기 소유 stdlib IPC만 허용하고 일반 직접 연결 차단을 따로 확인했습니다.

다음 구체적 단계는 앱 서버를 loopback으로 띄우고 격리 브라우저에서 실제 화면을 검사할지 선택받는 것입니다. 서버·브라우저 확인과 실제 모델/Google 연결은 별도 게이트입니다. 아직 접속 URL이나 실연동 성공을 전달하지 않습니다. 원래 백엔드 인수 후 부모 변경은 반복/교차일 규칙과 시간대 설정/공개 오류 경계이며, 기존 백엔드 시험은 보존했습니다. 코드와 현재 기록을 선택된 Git 단위 방식으로 함께 기록하고, 비공개 인증값·DB·원시 로그는 제외합니다.

관찰된 RED→GREEN을 기록하고 import 오류를 행동 테스트의 RED로 세지 않습니다. 자녀 결과를 기다리려고 로그·산출물을 반복 조회하지 않으며, 메인은 독립 화면 작업을 진행한 뒤 정상 결과 전달을 받습니다.

설치와 외부 호출은 별도입니다. 설치 승인만으로 서버·브라우저·Google 로그인·모델·캘린더 요청을 시작하지 않습니다. 모델·Google 연결부는 테스트에서 명시적 대역을 쓰고 실제 전송을 막습니다.

그다음 Cloud Console의 기존 옵시디안 프로젝트에서 새 과제용 Desktop app OAuth 클라이언트를 준비합니다. 제안 표시 이름은 `일정 등록 에이전트`입니다. 정확한 프로젝트와 Calendar API 상태를 확인하며, 기존 옵시디안 클라이언트나 프로젝트 공통 설정은 임의 수정하지 않습니다. 실제 생성·파일 저장·인증·실호출을 각각 확인합니다.

모델은 `gpt-5.6-luna`로 사용자 확정됐으므로 선택 질문을 반복하지 않습니다. 이전 `gpt-6-luna` 추천은 과거 비교 기록으로만 남깁니다. 공식 표준 요금과 예시 계산은 작업 명세서 9절에 있으며 실제 추론·혜택 적용 증거가 아닙니다.

연결 대상으로 기본 캘린더를 쓸지, Google Calendar 안의 별도 과제용 캘린더를 쓸지는 아직 미정입니다. 후자는 새 캘린더 앱 개발이 아니라 같은 Google 서비스 안의 분리된 일정 묶음입니다. 어느 쪽도 임의 생성하지 않습니다.

그다음 실제 입력 예시, 승인 기준 두 가지, 사용자 담당 판단, 기술 명세서와 구현 범위를 확정합니다. 모델·계정 준비가 안 됐다는 이유로 이미 합의한 요구사항을 처음부터 다시 인터뷰하지 않습니다.

## 7. 주요 결정 이유·한계·보류

- 기존 프로젝트에 억지로 붙이지 않고 독립 과제로 분리: 기존 기능의 범위와 회귀 부담을 늘리지 않기 위함.
- Google Calendar 실연동 유지: 실제로 쓸 수 있는 보조 에이전트를 만들려는 사용자 목표.
- 앱 내부 함수/API: 이번 과제에 별도 MCP 서버 운영을 추가하지 않음.
- 사람 검토 후보는 일시 정보 모호함과 일정 충돌. 아직 사용자 확정이나 실제 검증 결과가 아님.
- 원문 근거·코드 검증·사람 결정·외부 반영 기록을 구분. LLM의 확신도만으로 안전을 보장하지 않음.
- 기존 일정 수정·삭제, 참석자 초대, 메일·단체방 자동 수집, 공개 호스팅은 현재 범위 밖.
- 사용자 선택 이유·평가 정답·회고를 에이전트가 사용자 의견으로 임의 작성하지 않음.
- 기술 명세서 작성과 코드 범위는 승인됐으며 초안을 작성함. 후속 구현은 이 연결 계약을 읽고 실제 의존성 API와 재대조.
- 초기 전체 예상 1~3시간은 추정이며, 인증 설정 대기는 별도. 구현 소요시간 실측은 아직 없음.

## 8. 재개 방법

프로젝트 루트에서 작업 명세서·이 현황·CHANGELOG와 실제 파일을 함께 확인합니다. Git은 승인된 로컬 방식대로 사용하되 기존 변경을 먼저 구분합니다. 아직 없는 앱을 완료된 것으로 해석하거나, 문서의 시험 계획을 실행 증거로 취급하지 않습니다.
